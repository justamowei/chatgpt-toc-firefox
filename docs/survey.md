調查日期：2026 年 10 月 2 日（Asia/Taipei）  
適用範圍：電腦瀏覽器中的 ChatGPT Web 長對話  
文件狀態：公開資料調查與可執行方案；尚未在你的帳號重現或測試工具

**2026-10-02 決策更新：已選擇直接自製，Firefox為第一優先；使用者已恢復開發，v0.1原型已建置並執行原生合成自測。Git每功能／30分鐘commit、每次push與SHA核對持續執行，私人儲存庫：https://github.com/justamowei/chatgpt-toc-firefox 。後續以docs/development-plan.md v1.4與原型驗收報告為準；本文保留作當次調查背景，未在使用者帳號確認OpenAI根因。**

## 1. 決策摘要

你的問題有相符的公開回報。官方曾公布長對話目錄功能，而使用者從 8 月起陸續回報目錄消失、舊訊息逐段載入；9 月底仍有相似回報。目前查閱的官方資料沒有確認永久移除，也沒有提供這個問題的根因或修復日期。[官方功能說明](https://help.openai.com/en/articles/6825453-chatgpt-release-notes)、[8 月回報](https://community.openai.com/t/long-conversation-navigation-regressed-table-of-contents-disappeared-and-older-messages-only-load-progressively/1391666)、[9 月底回報](https://community.openai.com/t/please-restore-two-navigation-features-removed-in-the-recent-ui-update/1401021)

**工作假設：優先調查長對話的歷史載入、分頁邊界與目錄初始化是否互相依賴。這是根據回報的推論，尚非 OpenAI 確認的原因。** 另外保留介面改版、帳號分批開放及顯示條件變動等可能性。

建議採取三階段：

1. 用固定對話做對照測試，確認你的問題屬於哪一類，並產出可交給客服的重現資料。
2. 評估現有導航工具能否解決日常使用；通過驗收就採用，不必立即自製。
3. 現有工具不符合需求時，建立本機導航擴充功能，並以離線閱讀器補足超長歷史的搜尋。完整的原生修復仍需要 OpenAI 處理。

本次交付為調查與企劃，未安裝擴充功能、修改帳號、提交客服案件或開始開發。

### 2.4 本次調查的邊界

- 這是針對功能、回報與替代方案的公開資料調查，不是統計抽樣；不同討論串可能有同一人重複發言。
- 社群中的客服轉述、廠商技術解釋與使用者猜測，均不等於 OpenAI 的正式根因分析。
- 尚未確認你的瀏覽器版本、方案、首次發生時間、視窗寬度與對話分支情況。
- 目錄消失本身不能證明歷史資料被刪除；是否完整須另外核對已知首則、特定舊訊息及匯出資料。
- 結論僅代表截至調查日可取得的資料，不宣稱全體使用者都遇到，也不宣稱已全面修復。

## 3. 原因假設與驗證方法

以下優先順序是調查判斷，沒有足夠資料可給出可信的百分比。

| 假設 | 優先度 | 怎麼驗證 | 哪些結果會降低可能性 |
|---|---|---|---|
| 目錄初始化依賴完整歷史或「已到最前端」狀態 | 高 | 記錄初開、分段載入、抵達已知首則時的目錄變化 | 短對話且完整載入仍穩定缺失 |
| 切換對話／重整後，目錄索引或載入邊界未正確重建 | 高 | 恢復目錄後切到另一聊天，再返回並重整 | 每次返回皆維持正常，僅首次出問題 |
| 新介面、帳號功能旗標或開放條件不同 | 中 | 同帳號跨瀏覽器；有合法可用的另一帳號時，再對照相近對話 | 缺失只出現在單一瀏覽器設定檔 |
| 視窗寬度、縮放或其他面板遮住入口 | 中 | 最大化、100% 縮放、關閉側邊面板後比較 | 足夠寬度下仍缺失，且其他瀏覽器一致 |
| 擴充功能、設定檔或暫存干擾 | 中低 | 新設定檔或無痕登入同帳號，不啟用其他擴充功能 | 乾淨環境與原環境結果相同 |
| 歷史載入請求失敗 | 待排除 | 對照 Network／Console 錯誤與缺失時間 | 無請求失敗只能降低此假設，不能排除資料或前端邏輯問題 |

「延遲載入」是尚未把舊內容取回；「虛擬化」是內容可能已取得，但只把部分放進目前頁面。兩者可同時存在。診斷時應分開記錄，避免把 DOM 裡沒有訊息直接判成資料不存在。

## 4. 第一階段：30–60 分鐘診斷與暫時恢復

### 4.1 固定測試材料

先挑三個不含敏感內容的對話，記錄已知首則提問、特定中段提問、最後一則提問；以「使用者提問數／助手回答數」分別計數。

- 短對照組：至少六個已完成回答，總內容不長。
- 中對照組：約 50–150 次使用者提問。
- 長對照組：目前實際受影響的長對話；若可選，含 300 次以上提問。

這些數量是測試分組，不是新的官方觸發門檻。沒有這麼長的對話時，使用現有樣本，不需為測試刻意生成大量內容。

### 4.2 執行順序

1. 記錄環境、目錄初始狀態與畫面截圖，再做修改。將視窗最大化、縮放設為 100%，比較入口是否只是被擠掉。
2. 在同帳號的乾淨瀏覽器設定檔／無痕中測試相同對話；無痕需確認沒有額外允許的擴充功能。
3. 在聊天內容區向上捲，等待較早訊息載入；記錄目錄何時出現。可嘗試 Ctrl+Home，但它可能只到目前載入區段的頂端，必要時重複操作。這項捷徑限制有使用者回報，不能保證一次抵達首則。[回報來源](https://community.openai.com/t/long-conversation-navigation-regressed-table-of-contents-disappeared-and-older-messages-only-load-progressively/1391666)
4. 若目錄恢復，切換聊天再返回、重整一次，驗證恢復是否持續。
5. 已知首則出現後仍無目錄，或測試超過十分鐘仍無進展，就停止反覆載入，轉向替代導航與客服重現資料。

清快取不是主要解法。只有乾淨設定檔正常、原設定檔異常時，才進一步處理原設定檔。分支聊天可能改變工作脈絡，因此不列為預設修復步驟。

### 4.3 診斷紀錄表

| 對話代號 | 初開目錄 | 載入舊訊息後 | 已知首則可見 | 返回／重整後 | 測試耗時 | 備註 |
|---|---|---|---|---|---|---|
| 短 | 待測 | 待測 | 待測 | 待測 | 待測 | 回答數、寬度 |
| 中 | 待測 | 待測 | 待測 | 待測 | 待測 | 是否分支 |
| 長 | 待測 | 待測 | 待測 | 待測 | 待測 | 是否持續要求舊歷史 |

## 5. 方案比較與選擇門檻

| 方案 | 成本／時間規劃 | 適合情境 | 實際限制 | 決策 |
|---|---|---|---|---|
| 載入較早訊息，嘗試恢復原生目錄 | 當日，約 30–60 分鐘診斷 | 偶發、短中篇對話 | 可能失敗或重整後復發 | 先試一次 |
| 現有導航擴充功能 | 每款約 1–2 小時驗收；價格與可用性以當時版本為準 | 希望繼續在原 Web 聊天 | 廠商宣稱須驗證；頁面改版可影響功能 | 優先評估 |
| 自製本機導航擴充功能 | 約 6–9 人日；先做可行性探索 | 需要可控權限、中文介面、特定流程 | 尚未載入歷史的取得與定位是主要難點 | 候選工具未通過才啟動 |
| 官方匯出＋本機閱讀器 | 約 2–4 人日；匯出等待另計 | 回查、搜尋、歸檔歷史 | 不即時；不同帳號／工作區匯出資格不同 | 作長歷史備援 |
| OpenAI 原生修復 | 排程與成本無法由使用者控制 | 所有 Web 長對話 | 需產品團隊處理 | 同時提交可重現案件 |

**採用現有工具的門檻：** 三個測試對話的已知首／中／尾提問均可被定位；對未收錄歷史有清楚提示；切換聊天不串資料；在你的環境中權限與資料流可接受。只測近期幾則能跳轉，不足以驗收。

若需求只是查舊資料，優先離線閱讀器。若需要邊聊天邊跳回舊提問，優先 Web 導航。兩種模式應明確區分，避免宣稱離線備份能修復原生 Web 介面。

## 6. 自製方案：ChatGPT 對話導航器 MVP

### 6.1 成功定義

讓使用者能看見已知的提問列表、搜尋、跳到正確位置；當資料不完整或目標尚未載入時，明確說明狀態並提供下一步。目錄完整度和跳轉能力是兩項分開驗收的能力。

MVP 支援 Chrome／Edge 桌面瀏覽器、一般文字聊天及目前所選分支。第一版不擴及桌面 App、手機、雲端同步、跨帳號搜尋或自動 AI 摘要。

### 6.2 必要功能

- 可收合的右側提問目錄：順序編號＋原提問摘要；附件型提問使用可取得的檔名或中性標籤。
- 提問文字搜尋：標示搜尋範圍是已收錄資料或完整離線快照。
- 目前位置高亮、回到剛才位置、鍵盤可操作的列表。
- 新提問與回答更新後增量更新；切換聊天時清空舊畫面並載入正確索引。
- 狀態提示：已收錄 N 則／完整度未知、正在載入較早訊息、目標尚不可定位、已取消。
- 一鍵停止載入；找不到目標時提供離線閱讀入口或手動載入提示。
- 設定與書籤留在本機；預設不永久保存整段聊天，提供清除資料功能。

回答 H2／H3 子目錄列為第二版。它有價值，但第一版先完成可靠的提問索引與跳轉。

### 6.3 資料與導航架構

```mermaid
flowchart LR
    A[頁面已載入訊息] --> B[訊息辨識與分支處理]
    C[使用者匯入的官方資料] --> B
    B --> D[本機索引與完整度狀態]
    D --> E[目錄與搜尋]
    E --> F{閱讀模式}
    F -->|離線快照| G[本機定位與高亮]
    F -->|即時 Web| H[載入與定位協調器]
    H --> I[定位成功或明確降級提示]
```

兩個來源產生的索引保留來源與時間戳，不能把舊匯出當作當前聊天的完整狀態。索引最少記錄：conversation ID、可取得的 message ID、branch ID／分支指紋、角色、摘要、資料來源、快照時間與完整度。缺少穩定 ID 時，複合指紋只能用來輔助去重，不能據此保證精準跳轉。

**即時 Web 模式：**

1. 先收錄頁面可取得的內容，以明確提示表示歷史可能尚未完整。
2. 使用者按「載入較早訊息」後，才啟動逐批載入；索引累積保留，不因 DOM 卸載而消失。初版每次操作上限設定為 60 秒或 20 批，實測後調整。
3. 預先記錄目前訊息與相對位置；結束或取消後嘗試恢復。無法恢復時給出可操作的提示。
4. 點擊已掛載目標，可直接捲動並高亮；尚未掛載時，透過已驗證的頁面行為逐步尋找，並允許取消。
5. 到達已知第一則、看到「沒有更早資料」的可靠訊號，或資料來源可核對完整範圍時，才考慮標記完整。沒有可靠訊號就維持「完整度未知」。

**離線模式：**

1. 使用者主動匯入官方匯出；開發前以去識別化樣本確認格式，不假定固定檔名或單一 JSON 結構。
2. 按實際分支結構重建閱讀順序，將工具訊息與附件缺漏清楚標示；無法判斷分支時要求選擇，不混合成一條。
3. 使用固定訊息錨點，搜尋與跳轉在本機完成。完整性只針對匯入快照中已核對的資料。

**可行性關卡：** 不預設 ChatGPT 提供公開的歷史讀取或任意 message ID 跳轉介面。未文件化介面若納入探索，須獨立成可替換的實驗 adapter，先驗證權限、格式與穩定性；失效時停用。不得把它當成正式公開 API，也不得在提案階段承諾所有舊訊息立即跳轉。

這個關卡若未通過，正式範圍就縮為「已收錄內容導航＋完整離線閱讀」，並在介面與交付說明中寫清楚。

### 6.4 權限、資料與效能

- 採 Manifest V3；優先使用使用者按鈕啟動的 activeTab／scripting，或只對 chatgpt.com 申請選用權限。Google 文件支持採最少必要權限。[Chrome 權限與隱私指引](https://developer.chrome.com/docs/extensions/develop/security-privacy/user-privacy)
- 不讀取或保存登入憑證，不送聊天到外部服務。內容用安全文字節點呈現；若保留富文字，必須先清理不可信 HTML。
- 暫存按帳號／工作區／對話／分支隔離；身份或工作區改變時清理，不能只靠網址相同就重用。清除流程包含索引、書籤及匯入快照。
- 預設只保存必要摘要與書籤，全文快照另由使用者主動匯入或保存；聊天資料不使用同步儲存。
- 監聽訊息容器並合併更新，避免每次變動重掃整頁；長目錄本身可採虛擬化，但完整索引保存在資料層。
- 頁面結構不符合預期時停止自動操作，提示版本不相容。

## 7. 驗收與效益衡量

下列是設計目標，未經實測。效能報告需附實際硬體、瀏覽器、對話大小與網路條件。

| 項目 | 驗收方法 | 目標 |
|---|---|---|
| 已掛載訊息定位 | 固定對話隨機取 20 個已收錄提問 | 全部落在正確訊息；觸發至高亮 p95 ≤ 1 秒 |
| 索引完整度 | 以已核對快照核對訊息 ID 與分支 | 快照範圍內不漏項、不重複；不能確認時不顯示完整 |
| 未載入歷史 | 點選 10 個尚未掛載目標 | 成功定位或明確說明尚不可達；不誤跳、不無限載入 |
| 搜尋 | 1,000 則提問摘要的本機固定資料集 | 查詢至結果 p95 ≤ 300 ms；清楚標示範圍 |
| 對話／分支切換 | 切換 10 次，含編輯提問、重新生成 | 不串聊天、不混分支、不使用失效錨點 |
| 取消與恢復位置 | 載入中取消與切換聊天 | 停止後續操作，恢復原位置或顯示恢復入口 |
| 資料流 | 檢查權限與網路紀錄 | 自製導航器不向外傳送聊天內容 |
| 可用性 | 用 5 個指定舊提問，比較手動找尋與工具 | 中位完成時間減少至少 50%；找錯次數不增加 |

另測：短／中／超長對話、文字＋程式碼＋表格、附件型提問、窄視窗、深淺色、離線／請求錯誤、重整、DOM 結構變動。若完整索引無法取得，縮小搜尋範圍，而不是默默給出漏項結果。

## 8. 執行排程與投入

以下為規劃估算，不是報價；實際投入取決於第一天的可行性驗證。建議由一位工程師完成開發，另安排使用者或測試人員驗收約一人日。各階段工期可重疊，不能直接等同日曆天數。

| 階段 | 工作 | 交付／決策 | 預估投入 |
|---|---|---|---|
| A | 重現問題、測試候選工具、整理客服資料 | 選用既有工具，或批准自製範圍 | 0.5–1 人日 |
| B | 驗證資料來源、分支辨識與歷史定位 | 可行性結果；明確決定即時與離線支援範圍 | 1 人日 |
| C | 建立列表、搜尋、增量索引、定位狀態與取消 | 可安裝的本機原型 | 2–3 人日 |
| D | 處理切換、位置恢復、權限、失效降級 | 可供固定樣本測試的版本 | 1.5–2 人日 |
| E | 使用者驗收、修正、安裝及維護文件 | 驗收報告與正式本機套件 | 1 人日 |

自製即時導航器總投入抓約 6–9 人日。完整離線閱讀器若獨立開發，另抓 2–4 人日；等待官方匯出不計入開發工時。商店公開上架、雲端同步、全平台支援均不在此估算內。

既有工具若通過 A 階段驗收，結案為「工具採用＋使用流程＋官方回報」，不啟動 B–E。若 B 階段發現歷史不可可靠取得或定位，停止承諾完整即時導航，改做離線閱讀器或有限索引版本。

## 9. 給 OpenAI 的修復建議

以下是產品與架構建議，不是對現有內部程式碼的描述。

1. **把導航索引與訊息渲染分離。** 對話開啟時先取得目前分支的輕量提問索引，正文繼續分頁載入；索引不應依賴目前 DOM 有多少訊息。
2. **提供按訊息定位的載入能力。** 點選提問後取得該訊息附近的一段內容，避免逐批穿過所有中間歷史。
3. **明確管理歷史邊界。** 第一則抵達、已無更早資料、載入失敗與尚在載入應為不同狀態，避免目錄等待永遠不成立的條件。
4. **重建與保留每個對話的狀態。** 切換聊天、重整、切分支、編輯／重新生成後都要核對索引，避免共用狀態污染。
5. **讓入口可預期。** 符合條件的長對話保持目錄按鈕；若索引未完成，顯示載入或錯誤狀態，避免入口直接消失。
6. **監測導航本身。** 追蹤符合條件卻無入口的比例、索引完成率、定位成功率與定位延遲；搭配長對話及分支回歸測試。
